1. Configuration File Migration

The foundation of any migration. Configuration files define what the AI coding assistant knows about your project and what it's allowed to do.

1.1 CLAUDE.md → AGENTS.md / instructions

Claude CodeOpenCode EquivalentReplacement Strategy
File: CLAUDE.md
Loading: Walks directory tree upward, auto-discovers and concatenates all CLAUDE.md files
Imports: @path/to/file.md inline syntax
Local override: CLAUDE.local.md (gitignored) 		File: AGENTS.md
Loading: Explicit "instructions" array in opencode.json with glob support
Substitution: {file:path/to/file} for inline file content
No auto-discovery — every instruction file must be listed
  1. Run /init in OpenCode to auto-generate AGENTS.md (reads existing CLAUDE.md, .cursorrules, .windsurfrules)
  2. List all instruction files in opencode.json:
// opencode.json
{
  "instructions": [
    "AGENTS.md",
    "CONTRIBUTING.md",
    "docs/guidelines/*.md"
  ]
}
CLAUDE.local.md → options:
A.Create AGENTS.local.md (gitignored), add to instructions array
B.Use ~/.config/opencode/opencode.json with personal instruction files
@imports → list all files explicitly; glob patterns cover whole directories
If your repo already uses AGENTS.md: OpenCode natively reads it. Claude Code reads CLAUDE.md instead (though it can import AGENTS.md). If you maintain AGENTS.md for Cursor or Windsurf, OpenCode picks it up directly — no duplication needed.

1.3 settings.json → opencode.json

Claude Code SettingOpenCode Config KeyReplacement Strategy
permissions.allow"permission": { "bash": "allow" }Direct mapping.
permissions.deny"permission": { "edit": "deny" }Direct mapping.
permissions.ask"permission": { "bash": "ask" }OpenCode supports allow, ask, deny per tool category with wildcard pattern matching. "Last matching rule wins."
permissions.defaultModeSet per-tool defaultsNo multi-mode system — set a permission per tool. Most default to allow; external_directory and doom_loop default to ask.
model"model": "anthropic/claude-sonnet-4-20250514"Provider-prefixed model ID. Set globally or per-agent. Cannot switch mid-session via slash command.
env{env:VAR} syntaxUse for variable substitution in config values and templates.
sandboxNo equivalentUse Docker, macOS sandbox profiles, or Linux seccomp externally.
autoMemoryEnabledNo equivalentMaintain AGENTS.md manually; make instruction file updates part of code review.
hooksPlugin event hooksOpenCode plugins support event hooks (tool.execute.before, session.start, etc.) for JS/TS-level automation. See Section 4.
additionalDirectoriesNo equivalentLaunch OpenCode from project root, or use external_directory permission to allow access outside the workspace.
Note: OpenCode model IDs include a provider prefix (e.g., "anthropic/claude-sonnet-4-20250514"), unlike Claude Code which infers the provider from the API connection.

1.4 Auto Memory → Manual Context

Claude CodeOpenCode EquivalentReplacement Strategy
Claude Code automatically saves learnings, preferences, and debugging insights to ~/.claude/projects/<project>/memory/. These accumulate across sessions. No auto memory. OpenCode treats each session independently. All project knowledge lives in instruction files. 
# 1. Export existing memories before migrating
cat ~/.claude/projects/*/memory/MEMORY.md

# 2. Manually curate into AGENTS.md
# Key conventions, build commands, debugging patterns

# 3. Make instruction updates part of code review
# Add a PR checklist item: "Updated AGENTS.md if new conventions discovered"

2. Skills & Commands

Claude CodeOpenCode EquivalentReplacement Strategy
Skills: .claude/skills/<name>/SKILL.md with YAML frontmatter
Commands: .claude/commands/<name>.md
Auto-invocation: Claude auto-loads skills matching task description
Dynamic injection: !`command` at load time 		Commands: .opencode/commands/<name>.md with YAML frontmatter
JSON config: "command" key in opencode.json
Invocation: /name with $ARGUMENTS, $1, $2 placeholders
Dynamic injection supported: `!`cmd`` and @filename in templates 		File-based command migration: 
# .opencode/commands/deploy.md
---
description: Deploy the application
agent: build
model: anthropic/claude-sonnet-4-20250514
---
Deploy the application:
1. Run tests: `!`npm test`!`
2. Build: `!`npm run build`!`
3. Push to $ARGUMENTS
JSON-based command migration: 
// opencode.json
{
  "command": {
    "deploy": {
      "template": "Deploy:\n1. Run tests\n2. Build\n3. Push to $ARGUMENTS",
      "description": "Deploy to a target environment",
      "agent": "build",
      "model": "anthropic/claude-sonnet-4-20250514"
    }
  }
}
Frontmatter mappings:
description→ "description"
context: fork→ Use "subtask": true to run in a subagent (isolated context)
allowed-tools→ "permission" on the agent definition
model→ "model" with provider prefix
arguments→ $ARGUMENTS, $1, $2 positional params
paths→ No equivalent — use agent scoping
No auto-invocation. Claude Code can automatically load skills when your task matches the skill's description. OpenCode commands must be invoked manually via /name. If you rely on auto-discovered skills, either invoke them manually or include that knowledge in globally-loaded instruction files.

3.2 AgentTeam, UltraThink & Other Advanced Features

Claude Code FeatureOpenCode StatusReplacement Strategy
AgentTeam Not available

Claude Code's AgentTeam launches multiple subagents in parallel with a shared task list. Agents spawn sub-agents and delegate subtasks.

Workarounds:

# Option 1: Run parallel sessions with different agents
opencode --agent frontend &    # Terminal 1
opencode --agent backend &     # Terminal 2

# Option 2: Shared task file for coordination
echo "- [ ] Refactor auth module
- [ ] Update API endpoints
- [ ] Write migration tests" > tasks.md

# Option 3: Orchestrate via Makefile
.PHONY: multi-agent
multi-agent:
  opencode -p "Review frontend: @frontend/src/**" &
  opencode -p "Review backend: @backend/src/**" &
  wait

For complex multi-agent workflows: LangChain, CrewAI, or CI pipeline DAGs.
UltraThink Partial

Claude Code's UltraThink enables extended reasoning with higher thinking budgets.

// opencode.json — Dedicated deep-thinking agent
{
  "agent": {
    "deep-thinker": {
      "description": "Extended reasoning for complex architecture",
      "mode": "primary",
      "model": "anthropic/claude-opus-4-20250514",
      "prompt": "Think deeply. Break down problems step by step.",
      "steps": 50
    }
  }
}

Use Claude Opus 4.x or OpenAI o-series models which support extended thinking. Pass provider-specific options (like reasoningEffort) through the agent config.
Explore agent Built-in OpenCode has built-in Explore (subagent for read-only research) and Scout (subagent for lightweight searches). No need to recreate — they're available by default.
Plan agent Built-in OpenCode has a built-in Plan agent (primary, restricted mode — changes require approval) and Build agent (primary, full access). Toggle with Tab. No need to recreate.
Plan Mode toggle Available Claude Code: Shift+Tab. OpenCode: Tab cycles between Build and Plan agents.
Context: fork Available Use "subtask": true on a command to run in an isolated subagent. Or invoke a subagent directly via @agent-name in the TUI.
Dynamic injection Available

OpenCode supports dynamic injection in command templates:

// Shell injection
The current branch is: `!`git branch --show-current`!`
Recent commits: `!`git log --oneline -5`!`

// File reference
Context from design doc: @docs/architecture.md
Subagent delegation Available Both tools support subagents. OpenCode has built-in General, Explore, and Scout subagents plus custom ones. Use @agent-name syntax or the task tool.
Context compaction Available OpenCode auto-compacts. Configure: "compaction": {"auto": true, "prune": 0.2, "reserved": 4000}.
Auto memory Not available Add learnings to AGENTS.md manually. Make instruction updates part of code review.
Terminal sandbox Not available Use Docker or macOS sandbox profiles externally.
Multi-model routing Available Set "model" per-agent. Mix providers: Haiku via Anthropic for quick tasks, Opus via Bedrock for heavy work.
Prompt caching Provider-dependent Anthropic provider supports prompt caching. Other providers vary.
Auto-update Available OpenCode supports "autoupdate": true (auto), false, or "notify" (alert only) in config.
Undo / Redo Available OpenCode /undo reverts changes + restores prompt (multiple consecutive). /redo reapplies. Uses file snapshots ("snapshot": true).
AgentTeam is the biggest architectural gap. No multi-session coordination in OpenCode. Use parallel sessions with shared task files, Makefile orchestration, or external frameworks like LangChain/CrewAI.

4. Hooks → OpenCode Equivalents

Claude Code has 24+ lifecycle events with five hook types. OpenCode has plugin event hooks (JS/TS-level) that cover many of the same scenarios, plus formatters for the most common use case.

Hook Use CaseClaude Code HookReplacement Strategy
Lint / format after edits PostToolUse on Write/Edit

OpenCode formatters (built-in + custom):

// opencode.json
{
  "formatter": {
    "prettier": {
      "command": ["npx", "prettier", "--write", "$FILE"],
      "extensions": [".js", ".ts", ".jsx", ".tsx"]
    },
    "eslint-fix": {
      "command": ["npx", "eslint", "--fix", "$FILE"],
      "extensions": [".js", ".ts", ".jsx", ".tsx"]
    }
  }
}

$FILE is replaced with the target file path. Formatters run automatically when files are written. Supplement with pre-commit hooks (husky, lefthook).
Block dangerous commands PreToolUse exits 2

Permission deny patterns with wildcards ("last matching rule wins"):

// opencode.json
{
  "permission": {
    "bash": {
      "*": "ask",
      "git *": "allow",
      "npm *": "allow",
      "rm *": "deny",
      "sudo *": "deny"
    }
  }
}
Session start setup SessionStart

OpenCode plugin event hooks (JS/TS):

// .opencode/plugins/setup.ts
export default function setup() {
  return {
    "session.start": async (ctx) => {
      await ctx.client.app.log("info", "Session starting");
      // Set up environment, warm caches, check deps
    },
    "shell.env": () => ({
      NODE_ENV: "development",
      API_URL: "http://localhost:3000"
    })
  };
}

Or use a wrapper script for simpler needs.
Desktop notifications Notification hook

Plugin hook or external tools:

// Plugin-based notification
"tool.execute.after": async (ctx) => {
  if (ctx.tool === "bash" && ctx.result?.exitCode !== 0) {
    // Send notification
  }
}

// Shell-based notification
# macOS: osascript -e 'display notification "Build done"'
# Linux: notify-send "Build done"
Prompt validation UserPromptSubmit Plugin hook: "message.send": intercept and validate prompts before sending to the model.
Post-edit context injection PostToolUse with additionalContext Plugin hook: "tool.execute.after": for post-edit actions. For context injection, use "experimental.session.compacting": hook.
Auto-commit on change PostToolUse + git External watcher or plugin hook monitoring "tool.execute.after" for write/edit events.
Config change detection ConfigChange OpenCode watches opencode.json natively. File watcher ("watcher": {"ignore": ["node_modules/**"]}) for other files.
OpenCode plugins provide hooks. While Claude Code's hook system is YAML/JSON-based with 5 types, OpenCode plugins are JS/TS modules that export hook functions for event categories: tool, session, file, command, message, permission, shell, and more. This is more flexible but requires JavaScript/TypeScript code instead of declarative config.

5. Plugins

AspectClaude CodeOpenCode EquivalentReplacement Strategy
Format .claude-plugin/plugin.json manifest JS/TS module exporting plugin functions, or npm package 
// .opencode/plugins/my-plugin.ts
import type { Plugin } from "@opencode-ai/plugin";

export default function myPlugin(): Plugin {
  return {
    "tool.execute.before": async (ctx) => {
      console.log(`Tool: ${ctx.tool}`);
    }
  };
}
Distribution Marketplace (official + community), git, zip npm registry (public or private), git, local files Publish to npm: "plugin": ["@org/opencode-plugin"]. Or share .opencode/plugins/ directory.
Loading /plugin install name@marketplace Auto-load from .opencode/plugins/ and ~/.config/opencode/plugins/. npm packages listed in "plugin" array are installed with Bun at startup. No interactive install — plugins are declarative. Dependencies in package.json are auto-installed.
Capabilities Skills, agents, hooks, MCP, LSP, monitors, settings Event hooks, custom tools, shell env injection, compaction hooks 
// Plugin with custom tool + env + hooks
export default function myPlugin(): Plugin {
  return {
    "tool.execute.before": async (ctx) => { /* ... */ },
    "shell.env": () => ({ MY_VAR: "value" }),
    tool: () => ({
      name: "my_tool",
      description: "Custom tool",
      args: { path: "string" },
      execute: async (args) => { /* ... */ }
    })
  };
}
Namespacing /plugin-name:skill-name No namespace system Use unique prefixes: /org-feature-name. Plugin custom tools can override built-in tools by name.
Marketplace Centralized discovery No centralized marketplace Distribute via npm. Document in team wiki or README.
OpenCode plugins are more powerful in some ways — they have full JS/TS programmability, can define custom tools, inject shell environment variables, and hook into many lifecycle events. The trade-off is they require coding instead of declarative YAML.

6. MCP Servers

Both tools support the Model Context Protocol. Configuration syntax differs; servers work identically.

AspectClaude CodeOpenCode EquivalentReplacement Strategy
Config location .mcp.json "mcp" key in opencode.json Translate config syntax (see example below).
Local (stdio) type: "stdio", separate command and args type: "local", command as array Combine command + args into a single array.
Remote (HTTP) type: "http" type: "remote" with url Rename type, move URL to top-level field.
SSE transport Deprecated Not available Migrate to HTTP (remote) before switching.
OAuth 2.0 Full OAuth with keychain storage OAuth supported with clientId, clientSecret, scope 
// opencode.json — OAuth MCP server
{
  "mcp": {
    "oauth-server": {
      "type": "remote",
      "url": "https://mcp.example.com",
      "oauth": {
        "clientId": "{env:MCP_CLIENT_ID}",
        "clientSecret": "{env:MCP_CLIENT_SECRET}",
        "scope": "tools:read tools:execute"
      }
    }
  }
}
Tool management Deferred loading via tool_reference Glob patterns with server name prefix: "mymcp_*": false Disable globally, re-enable per-agent. MCP tools are registered with server name prefix.
Channels (push events) Supported Not documented Poll-based invocation; external webhook handlers.
Elicitation (user dialogs) Supported Not documented Inline prompts; pre-configure MCP tool inputs.

Config Translation Example

// Claude Code: .mcp.json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" }
    },
    "local-db": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@bytebase/dbhub", "--dsn", "postgresql://..."]
    }
  }
}

// OpenCode: opencode.json
{
  "mcp": {
    "github": {
      "type": "remote",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer {env:GITHUB_TOKEN}" },
      "enabled": true
    },
    "local-db": {
      "type": "local",
      "command": ["npx", "-y", "@bytebase/dbhub", "--dsn", "postgresql://..."],
      "enabled": true
    }
  }
}

// Disable MCP tools globally, re-enable per-agent
{
  "tools": {
    "github_*": false
  },
  "agent": {
    "build": {
      "tools": {
        "github_*": true
      }
    }
  }
}
Key differences: (1) Claude Code uses type: "stdio" with separate command/args — OpenCode uses type: "local" with command as a single array. (2) Claude Code uses ${ENV_VAR} for env vars — OpenCode uses {env:ENV_VAR}. (3) OAuth IS supported in OpenCode.
