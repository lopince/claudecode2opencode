Authentication Setup

Claude Code

Run claude and follow browser login, or use /login. Supports Claude Pro/Max/Team/Enterprise subscriptions, API keys (Console), or cloud providers (Bedrock, Vertex AI). Credentials are stored and you won't need to re-authenticate.

OpenCode

Run opencode, then use /connect to select from 75+ providers and enter API keys. Credentials are stored at ~/.local/share/opencode/auth.json. For managed teams, subscribe to OpenCode Zen (curated verified models) or Go (low-cost subscription plan).

4. Configuration File Migration

4.1 CLAUDE.md → AGENTS.md / instructions Medium Effort

Claude CodeOpenCode
Files: CLAUDE.md, .claude/CLAUDE.md, CLAUDE.local.md
Loading: Walks directory tree upward, all discovered files concatenated
Imports: @path/to/file.md inline syntax
Managed: /Library/Application Support/ClaudeCode/CLAUDE.md (macOS) 		Files: AGENTS.md (standard), plus any markdown files
Loading: Explicit "instructions" array in opencode.json with glob support
Substitution: {file:path/to/file} for file content in config values
Managed: Enterprise central config file

Migration Steps

  1. Run /init in OpenCode to auto-generate an AGENTS.md from your codebase. OpenCode reads existing CLAUDE.md, .cursorrules, and .windsurfrules to bootstrap it.
  2. Convert CLAUDE.md content: Merge your CLAUDE.md conventions into AGENTS.md. List additional instruction files in opencode.json: 
    // opencode.json
{
  "instructions": [
    "AGENTS.md",
    "CONTRIBUTING.md",
    ".cursor/rules/*.md",
    "docs/guidelines/*.md"
  ]
}
  3. Handle CLAUDE.local.md: OpenCode has no direct equivalent. Options:
    • Keep personal preferences in ~/.config/opencode/opencode.json with an instructions array pointing to personal files
    • Create a gitignored AGENTS.local.md and add it to the instructions array
  4. Handle @imports: OpenCode doesn't support in-file imports. List all instruction files explicitly in the instructions array. Use glob patterns for whole directories.
If your repo already uses AGENTS.md: Claude Code reads CLAUDE.md not AGENTS.md (though it can import it). OpenCode natively uses AGENTS.md. If you're already maintaining an AGENTS.md for other tools like Cursor or Windsurf, OpenCode picks it up directly — no duplication needed.

4.2 .claude/rules/ Migration Medium Effort

Claude Code's .claude/rules/ directory supports path-scoped rules (YAML frontmatter with paths: glob patterns) that only load when Claude works with matching files. OpenCode loads all instruction files globally — there is no path-scoped equivalent.

Three Migration Approaches

ApproachHow It WorksBest For
A. Flatten Merge all rules into AGENTS.md or a single instruction file. Group by topic with markdown headers. Accept the context cost of always-loaded instructions. Small-to-medium projects; short rules files
B. Agent-based Create specialized OpenCode agents for different parts of the codebase, each loading relevant instruction files. A frontend agent loads frontend rules; a backend agent loads backend rules. Large projects with clear domain boundaries; monorepos
C. Command-based Convert path-specific rules into custom commands that users invoke when working in specific areas. The command loads the relevant context as part of its template. Rules that are task-oriented rather than always-on

Agent-based example:

// opencode.json
{
  "agent": {
    "frontend": {
      "description": "Frontend development — React, TypeScript, CSS",
      "prompt": "{file:./opencode/agents/frontend-prompt.md}",
      "model": "claude-sonnet-4-6"
    },
    "backend": {
      "description": "Backend development — Go, PostgreSQL, gRPC",
      "prompt": "{file:./opencode/agents/backend-prompt.md}",
      "model": "claude-sonnet-4-6"
    }
  }
}

4.4 Auto Memory → Manual Context Low Effort

Claude Code's auto memory system (~/.claude/projects/<project>/memory/) automatically saves learnings, preferences, and debugging insights across sessions. OpenCode has no equivalent — it relies entirely on instruction files you manage.

Migration Strategy

  1. Export before migration: Review your project's auto memory at ~/.claude/projects/<project>/memory/MEMORY.md. Extract key conventions, build commands, and debugging patterns.
  2. Fold into AGENTS.md: Incorporate the valuable learnings into AGENTS.md or instruction files. These become permanent team knowledge.
  3. Maintain proactively: When the team discovers patterns or conventions, add them to AGENTS.md manually — OpenCode won't do this automatically. Make instruction file updates part of your code review process.

Command Migration Example

# ── Claude Code ──────────────────────────────
# .claude/commands/deploy.md
---
description: Deploy the application
disable-model-invocation: true
---
Deploy the application:
1. Run tests
2. Build
3. Push to $ARGUMENTS

# ── OpenCode ────────────────────────────────
# opencode.json
{
  "command": {
    "deploy": {
      "template": "Deploy the application:\n1. Run tests\n2. Build\n3. Push to $ARGUMENTS",
      "description": "Deploy the application to a target environment",
      "agent": "build"
    }
  }
}

Skill Frontmatter Mapping

disable-model-invocationNot needed — OpenCode commands are user-invoked by default; no automatic model invocation

Gap: No auto-invocation. Claude Code can automatically load skills when your task matches the skill's description. OpenCode commands are only invoked when you type /name. If you rely on Claude auto-discovering skills (e.g., a skill that teaches API conventions), you'll need to either invoke it manually or include that knowledge in a globally-loaded instruction file instead.

6. Hooks → OpenCode Equivalents High Effort

This is the largest migration gap. Claude Code's hook system provides 24+ lifecycle events with five hook types (command, HTTP, MCP tool, LLM prompt, subagent). OpenCode has no equivalent hook infrastructure.

Common Hook Scenarios & Replacement Strategies

Use CaseClaude Code HookOpenCode Replacement
Lint after edits PostToolUse on Write/Edit → runs ESLint, Prettier OpenCode formatters provide the closest equivalent:
"formatter": { "prettier": { "extensions": [".ts"] } }
Or a custom formatter: "custom": { "command": ["npx", "eslint", "--fix", "$FILE"] }
Supplement with pre-commit hooks (husky, lefthook)
Block dangerous commands PreToolUse hook exits 2 for rm -rf Permission deny patterns: "rm -rf *": "deny"
System-level: restricted sudo, shell aliases, Docker seccomp profiles
Session start setup SessionStart sets env vars, warms caches, checks deps Wrapper script (bash/zsh) that runs setup before launching opencode
Desktop notifications Notification on idle/auth/permission events External notification tooling: terminal-notifier, tmux hooks, osascript
Prompt validation UserPromptSubmit can block prompts matching patterns No direct equivalent — rely on team conventions and code review
Post-edit context injection PostToolUse with additionalContext returns guidance No equivalent — OpenCode doesn't support runtime context injection. Redesign the workflow
Auto-commit PostToolUse runs git add + git commit External file watcher (e.g., watchexec) or periodic cron
Config change detection ConfigChange reloads config on file change OpenCode watches opencode.json natively; restart for other files

Formatters: The Closest Built-in Alternative

OpenCode's formatter system covers the most common hook use case — auto-formatting and linting on file save:

// opencode.json
{
  "formatter": {
    "prettier": {
      "extensions": [".js", ".ts", ".jsx", ".tsx", ".json", ".md"]
    },
    "eslint-fix": {
      "command": ["npx", "eslint", "--fix", "$FILE"],
      "extensions": [".js", ".ts", ".jsx", ".tsx"],
      "environment": { "NODE_ENV": "development" }
    }
  }
}
$FILE substitution: OpenCode replaces $FILE with the target file path before running the formatter command. Formatters run when a file is written within the session.

AspectClaude CodeOpenCode
Manifest.claude-plugin/plugin.json — name, version, authornpm package.json or direct file placement
DistributionMarketplace (official + community), git repo, zip archivenpm registry (public or private), git repo, direct file placement

Conversion Steps

  1. Skills & Commands: Move from skills/<name>/SKILL.md to .opencode/commands/<name>.md or .opencode/skills/<name>/. Convert YAML frontmatter to OpenCode command config fields.
  2. Agents: Convert Claude Code subagent definitions (.claude/agents/) to OpenCode agent configs in .opencode/agents/ or the "agent" key in opencode.json.
  3. Hooks: Replace hook-based automation with formatters, external watchers, and pre-commit hooks. See hooks section for scenario-by-scenario guidance.
  4. MCP servers: Transfer from .mcp.json to the "mcp" config key in opencode.json. Auth methods may need adjustment.
  5. LSP: Convert .lsp.json config to OpenCode's "lsp" key.
  6. Monitors: No equivalent — replace with external monitoring (watchexec, fswatch, tmux status bars).
  7. Ship it: Publish as an npm package or share via git with setup instructions. Reference in team opencode.json: "plugin": ["@your-org/opencode-frontend-tools"].
npm-based distribution: OpenCode can load plugins directly from npm — a capability Claude Code doesn't have natively. If your team already uses npm for package management, plugin distribution integrates with your existing workflow.

8. MCP Server Migration Low Effort

Both tools support the Model Context Protocol, making this one of the easiest migrations. The configuration syntax differs slightly, but the servers themselves work identically.

AspectClaude CodeOpenCode
Config location.mcp.json, ~/.claude.json"mcp" key in opencode.json
Transport typesHTTP (streamable-http), SSE (deprecated), stdioremote (HTTP with URL), stdio
OAuth 2.0Full OAuth with keychain storage, dynamic client registrationNot documented — use API-key-based auth where available
Tool searchDeferred loading via tool_reference blocksNot documented — all tools likely loaded upfront
ChannelsMCP servers push messages into sessionsNot documented
ElicitationMCP servers request user input mid-task via dialogsNot documented

Config Translation

// Claude Code: .mcp.json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" }
    },
    "local-db": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@bytebase/dbhub", "--dsn", "postgresql://..."],
      "env": { "NODE_ENV": "production" }
    }
  }
}

// OpenCode: opencode.json
{
  "mcp": {
    "github": {
      "type": "remote",
      "url": "https://api.githubcopilot.com/mcp/",
      "enabled": true
    },
    "local-db": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@bytebase/dbhub", "--dsn", "postgresql://..."]
    }
  }
}
Auth migration: If your team uses OAuth-authenticated MCP servers (Sentry, Notion, Slack via MCP), check whether those servers offer API-key-based authentication as an alternative. OpenCode doesn't document MCP OAuth support. For servers that only support OAuth, you may need an authentication proxy.

9. Permissions Migration Low Effort

OpenCode's permissions are simpler and less granular than Claude Code's. The default is permissive (allow all), whereas Claude Code defaults to prompting for writes and Bash.

Claude CodeOpenCode
Syntax: Tool(pattern) with deny→ask→allow precedence
Modes: default, acceptEdits, plan, auto, dontAsk, bypassPermissions
Granularity: Per-tool, per-path (gitignore patterns), per-command (Bash), per-domain (WebFetch), per-MCP-tool
Scopes: User, project, local, managed policy 		Syntax: "permission": { "edit": "ask" } with wildcard patterns
Values: allow, ask, deny
Granularity: Per-category (edit, bash) with command-level wildcards
Defaults: Allows all operations without approval

Translation Example

// Claude Code: .claude/settings.json
{
  "permissions": {
    "allow": [
      "Bash(npm *)",
      "Bash(git *)",
      "Read(/src/**)"
    ],
    "deny": [
      "Bash(rm *)",
      "Read(.env)",
      "Edit(//etc/**)"
    ],
    "defaultMode": "default"
  }
}

// OpenCode: opencode.json
{
  "permission": {
    "edit": "ask",
    "bash": "ask",
    "npm *": "allow",
    "git *": "allow",
    "rm *": "deny"
  }
}
Missing granularity: Claude Code's path-based Read/Edit deny rules (using gitignore patterns like Read(/src/**)) have no equivalent in OpenCode. Per-MCP-tool permissions and WebFetch domain rules also don't map. For strong file-level access control, consider OS-level permissions or containerization.

// OpenCode: opencode.json
{
  "agent": {
    "security-reviewer": {
      "description": "Reviews code for security vulnerabilities — OWASP Top 10",

Agent teams — the experimental multi-session coordination feature — have no migration path.

14. Migration Guidance by Project Type

🖥️

Standard Coding Projects

Primarily conversational AI pair programming — reading code, making edits, writing tests, git operations. Low-to-medium effort, 1–3 days.
🔧

Prompt/Skill-Driven Projects

Heavy use of custom skills, hooks, plugins, and subagents. High effort, 1–4 weeks, significant workflow redesign required.
📦

Monorepo Projects

Multiple packages, nested configs, path-scoped rules. Medium effort, ~1 week, agent-based approach recommended.

14.1 Standard Coding Projects Low–Medium Effort

For projects that use Claude Code primarily as an AI pair programmer:

Convert CLAUDE.md

Run /init to generate AGENTS.md, then merge any custom conventions from your CLAUDE.md. The daily conversational workflow is nearly identical.

Replicate permissions

Translate permission rules to OpenCode's simpler permission model. Configure "permission": { "edit": "ask", "bash": "ask" } if you want Claude Code's default prompting behavior.

Set up formatters

Configure formatters to replace any PostToolUse lint hooks.

Update CI/CD

Update CI pipelines to use opencode instead of claude.

Estimated effort: 1–3 days. Most of the work is configuration translation.

14.2 Prompt/Skill-Driven Projects High Effort

For projects heavily reliant on Claude Code's extensibility:

Audit your extensions

Inventory every skill, command, hook, plugin, subagent, and MCP server. Document what each one does and which team workflows depend on it.

Migrate skills & commands first

Convert .claude/skills/ and .claude/commands/ to .opencode/commands/. Replace !`cmd` dynamic injection with pre-computed context in wrapper scripts, or accept static templates.

Replace hooks — the hard part

For each hook, identify the appropriate replacement: formatters for lint-on-save, pre-commit hooks for guardrails, wrapper scripts for session setup, external watchers for auto-commit.

Recreate agents

Convert subagent definitions to OpenCode agents with appropriate tool restrictions. Recreate Explore-like agents for research tasks.

Restructure plugins

Package as npm modules or shared .opencode/ directories. Since OpenCode has no namespace system, ensure command names are globally unique.

Estimated effort: 1–4 weeks depending on hook complexity and number of plugins.

14.3 Monorepo Projects Medium Effort

Claude Code's nested CLAUDE.md discovery and path-scoped rules were built with monorepos in mind. OpenCode takes a flatter approach:

  1. Instructions: Use glob patterns in the instructions array to pull in rules from sub-packages
  2. Path-scoped rules: Use the agent-based approach — create specialized agents per package with their own instruction files
  3. No claudeMdExcludes needed: OpenCode only loads explicitly listed files — no risk of picking up unrelated configs
  4. Run from package directory: For focused work, launch OpenCode from a specific package directory with a package-specific opencode.json

15. Migration Checklist

Phase 1 — Assessment (1–2 days)

  • Inventory all CLAUDE.md files (project, user, managed) and their @imports
  • Inventory all .claude/rules/ files and their path scopes
  • Inventory all skills (.claude/skills/) and commands (.claude/commands/)
  • Inventory all hooks (in settings.json, settings.local.json, and plugins)
  • Inventory all plugins and their components (skills, hooks, MCP, agents, LSP, monitors)
  • Inventory all MCP servers and their authentication methods
  • Inventory all subagent definitions (.claude/agents/)
  • Inventory all permission rules and modes
  • Review auto memory at ~/.claude/projects/<project>/memory/ and extract valuable learnings
  • Identify CI/CD pipelines that invoke Claude Code
  • Survey team members on their daily workflow patterns and customizations

Phase 2 — Setup (1–2 days)

  • Install OpenCode on all developer machines
  • Configure providers and API keys via /connect
  • Run /init in each project to generate AGENTS.md
  • Set up global config at ~/.config/opencode/opencode.json
  • Configure desired model and default agent
  • Upgrade terminal emulator if needed (WezTerm, Ghostty, Kitty, or Alacritty recommended)

Phase 3 — Config Migration (2–5 days)

  • Merge CLAUDE.md content into AGENTS.md + instruction files

17. Commands Reference & Advanced Features

This section maps Claude Code's built-in slash commands and advanced capabilities — including AgentTeam and UltraThink — to their OpenCode equivalents. Use it as a quick reference during daily work and when planning which workflows need adaptation.

17.1 Slash Commands Mapping

/help /help Both show available commands and usage. OpenCode's help is context-sensitive based on your config.
/clear Start new session OpenCode has no in-session clear. Press Ctrl+C to interrupt, then start a fresh session. Session list available in TUI.
/model Edit opencode.json or use /connect OpenCode doesn't switch models mid-session via slash command. Set "model" in config or per-agent, or connect a different provider. Changing the active model for the default agent requires editing opencode.json and restarting.

/plugin Edit opencode.json "plugin" array Claude Code has /plugin install|uninstall|list. OpenCode loads plugins from .opencode/plugins/ or npm packages listed in config — no interactive install command.
/memory — Claude Code opens the auto-memory editor. OpenCode has no auto-memory system — maintain AGENTS.md manually.
/compact Automatic Claude Code lets you manually trigger context compaction. OpenCode handles context window management automatically — no manual trigger needed.
/review Natural language: "review this PR" Claude Code's /review triggers the code-review skill. In OpenCode, describe what you want reviewed — the agent will read and evaluate the code.
/security-review Natural language or custom command Claude Code has a dedicated security-review skill. In OpenCode, ask the agent to "do a security review" or create a custom /security-review command in .opencode/commands/.

/doctor — Claude Code runs system diagnostics. For OpenCode, manually check: Node.js version, provider connectivity, and config file validity.
/status — Claude Code shows session status, model, token usage. OpenCode doesn't have a status command — check the TUI header for the current model and agent.

17.2 AgentTeam, UltraThink & Other Advanced Features

Claude Code ships with several advanced features that power users rely on. Here's how they map — or don't map — to OpenCode.

Claude Code FeatureOpenCode StatusDetails & Workarounds
AgentTeam Not available

Claude Code's AgentTeam (experimental) launches multiple subagents in parallel, coordinates them via a shared task list, and merges results. Agents can spawn other agents, delegate subtasks, and hand off work.

Workaround: Run multiple OpenCode sessions in separate terminals with different agent configs. Use a task file or external orchestrator (Makefile, CI pipeline, custom script) to coordinate work. For complex multi-agent workflows, consider LangChain or CrewAI as an external orchestration layer.
UltraThink Partial

Claude Code's UltraThink mode enables extended reasoning with higher token budgets for complex problems. The model spends more time "thinking" before responding.

OpenCode equivalent: Use models that support extended thinking (Claude Opus 4.x with thinking parameter, OpenAI o-series). Configure the model in opencode.json with extended thinking enabled. Not all providers expose thinking budget controls — Claude models via Anthropic provider and OpenAI o-series models are your best options.

// opencode.json — using Claude with extended thinking
{
  "model": "claude-opus-4-7",
  "agent": {
    "deep-thinker": {
      "model": "claude-opus-4-7",
      "description": "Extended reasoning for complex problems",
      "prompt": "{file:./opencode/agents/deep-thinker-prompt.md}"
    }
  }
}
Plan Mode (thinking) Available via Tab toggle

Claude Code plan mode ensures the model plans before writing code. OpenCode's plan/build toggle (Tab) provides the same pattern: in plan mode the agent analyzes and designs; in build mode it makes changes.
Context: fork Available via subagents

Claude Code skills can run in a forked (isolated) context. OpenCode achieves this by running a task in a dedicated subagent — the subagent gets a clean context and returns results to the main session.
Dynamic injection (!`cmd`) Not available

Claude Code can execute shell commands at skill-load time and inject the output into the prompt. This enables context-aware skills that adapt to the current repo state.

Workaround: Create a wrapper script that pre-computes the dynamic context and appends it to a file, then reference that file in your instruction files. For commands that need live state, run a pre-step manually or via a wrapper before invoking the command.

# Example wrapper for dynamic context
#!/bin/bash
# pre-compute dynamic context
git log --oneline -20 > /tmp/recent-commits.txt
opencode -p "Review these recent commits: {file:/tmp/recent-commits.txt}"
Subagent delegation Available

Both tools let the main agent spawn subagents for parallel or isolated work. Claude Code has built-in Explore (read-only research) and Plan (architecture) agents plus custom ones. OpenCode supports custom agents with tool restrictions for the same patterns — create an "explore" agent with "write": false, "bash": false.
Compaction strategies Automatic

Claude Code offers manual (/compact) and automatic context compaction. OpenCode handles compaction internally — the model manages its own context window. No user control, but also no need to think about it.
Auto memory Not available

Claude Code learns from each session and persists insights to ~/.claude/projects/<name>/memory/. OpenCode treats each session independently. Team conventions and learnings must be manually added to AGENTS.md or instruction files.
Terminal sandbox Not available

Claude Code sandboxes Bash commands at the OS level (macOS Seatbelt, Linux landlock/seccomp). OpenCode has no sandbox — commands run with the user's full permissions. Use Docker, a VM, or macOS sandbox profiles externally for untrusted workloads.
Multi-model routing Available via agents

Claude Code can route different tasks to different Claude models (Haiku for simple edits, Opus for complex reasoning). OpenCode does this natively per-agent: set "model" on each agent definition. Plus you can mix providers — use Haiku via Anthropic for quick tasks and Opus via Bedrock for heavy work.
Prompt caching Provider-dependent

Claude Code uses Anthropic's prompt caching for cost savings on long conversations. In OpenCode, prompt caching behavior depends on the provider — Anthropic models support it; other providers may or may not.
AgentTeam is the biggest architectural gap. If your workflow depends on coordinated multi-agent work (parallel agents sharing a task list, spawning sub-agents, merging results), there is no direct substitute in OpenCode. Evaluate whether you can break the workflow into sequential steps, run sessions in parallel manually, or use an external orchestration framework like LangChain, CrewAI, or a CI pipeline DAG.
UltraThink / Extended thinking: When using Claude models via the Anthropic provider in OpenCode, extended thinking is controlled by the model configuration. Claude Opus 4.7 and Claude Sonnet 4.6 support configurable thinking budgets. The thinking tokens are not visible in the chat, but the model uses them internally for deeper reasoning — similar to how Claude Code's UltraThink works. Check your provider's documentation for thinking budget parameters you can pass through OpenCode's model config.
